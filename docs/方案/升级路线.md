## 0. 一句话

把链路从 **`文生视频`（T2VA）** 升级成 **`文生图关键帧 → 图生视频`（I2VA）**。
出图用 **Qwen-Image，跑在已有的 RunPod 上**。

## 2. 升级后会改变什么

| 环节 | 现在 | 升级后 |
|---|---|---|
| **分镜执行** | T2VA，构图交给模型即兴 | **I2VA/首帧**，从锁死的关键帧起步 |
| **跨镜一致性** | 只靠 1 张身份参考图（且这张图本身还得从 H3 视频里抽帧） | 每镜有关键帧锚定 |
| **定妆图** | **H3 出 4s 正脸视频 → 抽一帧**（自锚定） | Qwen-Image **直接出**，可用真正的角色三视图 |
| **镜头控制力** | 分镜是"建议" | 分镜是"施工图" |
| **平台数** | **2**（Claude Code + RunPod） | **仍是 2** —— Qwen-Image 跑在**同一个 RunPod** 上 |

> ⚠️ **重要修正**：方案 v2 §3 把"接云 T2I"列为 **B1 档（+1 个平台）**，原文是：
> **B1** 接云 T2I 出定妆图，H3 走 I2V → 解决 §2 唯一硬缺口（无 T2I）、跨镜脸/服装漂移 → 新平台：Seedream 4.0（或 Qwen-Image，二选一）
>
> **但 2026-10-09 的平台核查推翻了"必须加平台"这个前提**——见 §6。**开源出图模型可以直接跑在已经在用的 RunPod 上，所以这条升级不新增平台，仍属 A 档的"少平台"约束之内。**
> 改动的是**工作量与 GPU 时间**，不是平台数。

## 4. 成本（**GPU 时间，不是按张付费**）

因为跑在自己的 Pod 上，出图成本 = **GPU 分钟**，不是每张单价。

| 项 | 数量 | 估算 |
|---|---|---|
| 角色定妆图 | 4（陈默 / 老墨 / 沈青 / 邵元） | 几分钟 |
| 每镜首帧 | 13 镜 | 十几分钟 |
| 重抽 1.5× | — | 同上 ×1.5 |

> 参照：RunPod 4090 **$0.74/h**。**单集出图的 GPU 成本 < $0.5【推测】**，相对视频生成（单集 $0.7–8）**可以忽略**。
> **⚠️ 真正的成本不是钱，是"Pod 要多装一套模型 + 多跑一遍工作流"的部署与操作时间。**

## 5. 触发条件（**满足任一条才启动**）

1. 第一集过 G4 后，抽检发现**跨镜漂移 > 30%**（验收标准 L1 判据 2）
2. 或：T2VA 出来的画面**明显不按分镜**——景别错、关键道具丢失、构图偏离
3. 或：**要开做第 2 集**，需要系列级一致性（多角色、多场景、跨集复用）
4. 或：本集里某个**出脸镜反复重抽不收敛**

> 反过来说：**若第一集 T2VA 出来就够看，这条升级可以无限期搁置。**

## 6. 平台核查结论（**2026-10-09 已核实**）

### 6.1 结论

**出图模型用 `Qwen-Image`，跑在已有的 RunPod 上。不引新平台、不用国内平台、不用国外付费 API。**

### 6.2 为什么不是国内的即梦 / 豆包 / 火山方舟 ⛔

即梦要求 **+86 手机号 + 境内 IP（回国 VPN）**；火山引擎实名还额外要**中国境内支付方式**。
用户有 +86 号与国内实名，但**缺的是「境内 IP」**——从肯尼亚直连大概率被地域风控拦。**这不是"麻烦一点"，是走不通。**
（同理，**Wan2.6-T2I 只有阿里云 Model Studio 的纯云 API，无开源权重**，也走这条死路。）

### 6.3 为什么是 Qwen-Image

| 候选 | 许可 | 结论 |
|---|---|---|
| **Qwen-Image**（阿里，20B） | **Apache 2.0 可商用** ✅ | **选它**。专为出图训练；中文/中国人脸最强；FP8 可上 4090 |
| Wan2.1 `t2i-14B` | Apache 2.0 可商用 ✅ | **能做**（官方 README 明文 `--task t2i-14B`），但机制是 **T2V-14B 权重 + frame_num=1**，**视频模型兼差出图**，静图精细度预期降一档；RunPod 无官方模板要自装。**降为备份** |
| FLUX.1-dev | ❌ **非商用许可** | **排除**——发抖音赚钱**不合规** |
| FLUX.2 | — | **排除**——要 **96GB 显存** |
| Seedream 4.0（fal.ai 国际网关） | 可商用 | **备用**。$0.03/张、只需国际信用卡、境外直连；但既然 RunPod 已在用，没必要为这个开账号 |

> **关键发现**：H3 镜像作者 `ls250824` 的另一个镜像 **`run-comfyui-image` 已内置 Qwen-Image 2.1/2512**（视频侧引用 WAN2.2 + H3）——
> **同一套 ComfyUI 生态，几乎零额外部署成本。**

**出图规格（官方 README 实测 2026-10-09）**：

| 比例 | 输出 |
|---|---|
| 1:1 | 1328 × 1328 |
| 16:9 | 1664 × 928 |
| **9:16（我们）** | **928 × 1664** |

竖屏原生 **928×1664**，**比 H3 本地输出的 768×1366 还高**，当身份参考图绰绰有余。

> 💡 **另外留个钩子**：Qwen-Image **自带改图能力**（README 原话 "doesn't just create or **edit**"），另有独立的 **Qwen-Image-Edit**。
> 以后要做「**同一角色换装 / 换状态**」——本项目 10 集必然遇到——**改图比重新生成更能保一致**。这条以后单独评估。

### 6.4 与 H3 共存的代价

- **能共存**，同一 ComfyUI + 同一网络卷，**不必开新 Pod**
- **磁盘**（HuggingFace API 实测 2026-10-09）：
  | 项 | 体积 |
  |---|---|
  | Qwen-Image（bf16 仓库） | **53.7 GB**（文本编码器 15.5 + DiT 约 38） |
  | Qwen-Image 走 **FP8** | **≈ 30 GB**【推算，比 bf16 省一半】 |
  | H3（int8） | **67 GB** —— 见 [事实基线.md](../../.claude/rules/事实基线.md) |
  | **网络卷合计** | **≈ 100 GB** → 方案 v2 定的 **200GB 卷（≈$14/月）够用** |
- ⚠️ **更正**：先前调研报的「H3+Qwen-Image 共 61GB」**是错的**——H3 单独就 67GB。**以 HF API 实测为准。**
- **显存**：Qwen-Image 20B FP8 权重约 20GB + 文本编码器约 9GB【推测】→ **4090 24GB 上必须分组加载**（ComfyUI 可以，但慢），要舒服得上 **5090 32GB+**
- **4090 24GB 上 H3 与出图模型要串行**（一个跑完再跑另一个）
- ⚠️ 首次开机下模型 **10–15 分钟**——所以**出图和出片要在同一次 Pod 会话里做完**，别为一个定妆图单独开机

### 6.5 仍未核实

- Qwen-Image 在 4090 上 FP8 的**实际出图速度**（每张几秒）【推测】
- `run-comfyui-image` 镜像与 H3 模板 `a1nkufhzxq` 能否合并成**一个 Pod 一次装齐**

### 6.6 Qwen-Image 的 ComfyUI 工作流（**2026-10-10 已核实**，逐字来自仓库原始 JSON）

**模板**（`Comfy-Org/workflow_templates` 的 `templates/` 下）：

| 用途 | 文件 |
|---|---|
| **文生图（选它）** | `image_qwen_image_2_1_t2i.json` |
| 旧版 / 2512 | `image_qwen_image.json` · `image_qwen_Image_2512.json` |
| **改图（换装/换状态）** | `image_qwen_image_2_1_image_edit.json` |

**文生图关键节点**（2.1）：

| 作用 | 节点类型 | widget 值 |
|---|---|---|
| 扩散模型 | `UNETLoader` | `qwen_image_2.1_int8_convrot.safetensors` |
| 文本编码器 | `CLIPLoader` | `qwen3vl_8b_int8_convrot.safetensors` / 类型 `qwen_image` |
| VAE | `VAELoader` | `qwen_image_2.1_vae_bf16.safetensors` |
| **提示词** | **外层子图节点的 `widgets_values[0]`**（label `positive_prompt`） | 内部接 `TextEncodeQwenImage21` |
| 采样 | `KSampler` | `steps=25, cfg=1`（cfg=1 时 negative 不生效） |
| 出图 | `SaveImageAdvanced` | `["Qwen_image_2.1","png","8-bit","sRGB"]` |

> ⚠️ **2.1 的模型节点封在 subgraph 里**，顶层只露一个子图节点 + `ResolutionSelector` + `SaveImage`。**要改的是子图节点上的 widget**。

**9:16 尺寸**：`ResolutionSelector` 的 `widgets_values = [aspect_ratio, megapixels, multiple]`，
竖屏那一项字符串是 **`"9:16 (Portrait Widescreen)"`**。
填 `megapixels=1.0, multiple=8` → 推算 **768×1368**（≈ H3 本地的 768×1366，很贴）。
（若改用 2512 模板：直接设 `EmptySD3LatentImage` 的 width/height，官方映射 **9:16 = 928×1664**。）

**模型文件**（HF `Comfy-Org/Qwen-Image-2.1`）：

```
models/diffusion_models/qwen_image_2.1_int8_convrot.safetensors     6.76 GB
models/text_encoders/qwen3vl_8b_int8_convrot.safetensors            8.71 GB
models/vae/qwen_image_2.1_vae_bf16.safetensors                      0.64 GB
                                                        合计约 16.1 GB
```

> 比先前估的 30GB **小不少**（2.1 的 int8 版更小）。Pod 余 20G **够装**。

**改图保一致（换装/换状态）**：`image_qwen_image_2_1_image_edit.json`——
`LoadImage` 喂图 → 子图内收编辑指令，**用 `<image1>`…`<image10>` 指代参考图（image_1 是被编辑目标）**，
模型文件与 T2I **相同**。这是"同一角色换装"的官方路子。

**⚠️ 开机后唯一要核实的**：`ls` 一下镜像里是否预置了**上述确切文件名**
（调研只查了官方仓库、**没连 Pod**，所以镜像里有没有、叫什么，**未验证**）。
